# Tube tracker data files

`index.html` is the whole app. The JSON beside it is generated — don't hand-edit it.

| File | Generated by | Fetched at runtime? |
| --- | --- | --- |
| `nr-network.json` | `scripts/build-nr-network.py` | yes, on load |
| `extras-network.json` | `scripts/build-nr-network.py` | yes, on load |
| `track-geometry.json` | `scripts/build-tube-geometry.mjs` | yes, on load |
| `bus-routes.json` | `scripts/build-bus-routes.mjs` | only when the bus picker is opened |
| `regional-buses.json` | `scripts/build-regional-buses.mjs` | only when the bus picker is opened |
| `buses/<area>.json` | `scripts/build-regional-buses.mjs` | only when a route from that area is added |
| `tfl-tracks.json` | manual OSM extract | **no** — build input only |

Tube, Overground and Elizabeth line routes come live from
`https://tube.contact.ms/map/network`; everything above is merged on top of it.

## Regenerating

```sh
python3 scripts/build-nr-network.py      # National Rail, DLR, river, cable car
node scripts/build-tube-geometry.mjs     # track geometry (needs tfl-tracks.json)
node scripts/build-bus-routes.mjs        # London bus/coach list for the picker
node scripts/build-regional-buses.mjs    # buses outside London (slow; see below)
```

`track-geometry.json` is the one to re-run after `tfl-tracks.json` changes or
after the upstream network feed gains or renames stations. It snaps each route
edge onto the surveyed track geometry once, offline, and ships the result as
polyline-encoded midpoints — the page used to do that work on every load, which
cost ~650 ms of main-thread time on a desktop and several seconds on a phone.
Edges with no surveyed track fall back to a spline through the neighbouring
stations, computed in the browser, so a stale or missing file degrades the
shape of a few lines rather than breaking the map.

## How far the map reaches

The map used to stop at the TfL *Rail & Tube services* fringe — Guildford,
Reading, Luton, Gatwick, Shenfield, Gravesend. It now also covers four reaches
beyond it, defined as boxes in `REGIONS` at the top of
`scripts/build-nr-network.py`:

| Reach | Takes in |
| --- | --- |
| `wealden` | Tunbridge Wells and its branches — the Hastings line to Robertsbridge, the Uckfield line, the Oxted line to East Grinstead — plus Crawley, Horsham, and the Brighton main line as far as Burgess Hill |
| `southend` | Both Southend lines: c2c via Basildon to Shoeburyness, Greater Anglia via Wickford to Southend Victoria, plus the Crouch Valley branch |
| `oxford` | Reading to Oxford down the Thames, Oxford Parkway and Islip on Chiltern's way in, and the Banbury line as far as Tackley |
| `cambridge` | Both Cambridge lines — Great Northern via Royston, Greater Anglia via Audley End — plus the East Coast stops out to St Neots |

One known gap: **Cambridge North is not there.** TfL's line data has never
listed it — it opened in 2017 and no TOC's `StopPoints` response includes it —
so the Cambridge lines end at Cambridge. Hard-coding it the way
`luton-airport-dart` is hard-coded would put a dot on the map with no route
through it, which is worse than leaving it out.

Adding a fifth reach is one entry in `REGIONS` and a re-run. Two things to get
right:

**The boxes have to overlap.** `clip_ids()` keeps only the longest unbroken run
of in-extent stops on a route, so one excluded station in the middle of a
corridor does not leave a gap — it amputates everything beyond it, silently. A
new box needs to overlap whatever it connects to.

**A box is a blunt instrument.** It will pick up stations that happen to sit
inside it on a line that leaves and never comes back. `EXCLUDE` in the same
file is the list of those, matched on display name because `norm_name()` drops
the parentheses that are the only thing distinguishing, say, Reedham (Norfolk)
from Reedham in Surrey.

The page has three matching numbers in it: `maxBounds` and `minZoom` on the
Leaflet map, and `DARWIN_HUBS`. Darwin has no "everything in this rectangle"
call, so live trains are assembled by polling busy stations and following each
service out from them — nothing around Oxford or Cambridge appears on a London
hub's calling list, so each reach needs its own hub or it renders as a static
diagram. `darwinHubsForView()` then polls the hubs actually on screen first,
which is what keeps the cycle short now the list is 39 stations rather than 25.

## Buses outside London

TfL's bus API stops at the Greater London boundary and the map does not, so
routes in Oxford, Cambridge, Surrey, Crawley, Tunbridge Wells and Southend come
from OpenStreetMap instead — the only bus network covering all of them that
does not need a key. `scripts/build-regional-buses.mjs` pulls the route
relations from Overpass and writes two kinds of file:

- `regional-buses.json` — one row per service, merged into the same picker as
  the TfL catalogue. Small enough to load with it.
- `buses/<area>.json` — stops and road geometry, simplified to 8 m and
  polyline-encoded, fetched the first time a route from that area is added.

A regional route id carries its area (`oxford:5`, so `bus:oxford:5` as a line
id). TfL's own ids never contain a colon, and that is the whole test —
`isRegionalRoute()`.

**They do not move.** No regional operator publishes vehicle positions without
a partner key, so `pollBuses()` and `fetchBusStatus()` skip these routes
(`entry.live === false`) and the picker says so. The stops are OSM nodes, not
NaPTAN ones, so neither arrivals feed has heard of them either; `isRegionalStop()`
keeps the panel from asking and the empty board explains itself.

### Re-running it

Overpass refuses in two ways and they want opposite responses, which is most
of what the fetch layer is for:

| | Means | Response |
| --- | --- | --- |
| 429 | every slot on that mirror is busy | wait, with exponential backoff, and rotate mirrors |
| 504 | *this query* ran out of time on the server | waiting cannot help — halve the batch and try each half |

Batch size is not knowable up front: a long-distance coach relation is orders
of magnitude heavier than a town circular, so 25 relations is sometimes fine
and sometimes far too much. The splitting finds the right size per chunk. A
single relation Overpass still will not serve is logged and skipped rather
than being allowed to fail the whole run.

Every response is cached under `.cache/overpass`, so an interrupted run resumes
rather than starting again. Expect an hour or more for all six areas, mostly
spent waiting:

```sh
node scripts/build-regional-buses.mjs            # all six areas
node scripts/build-regional-buses.mjs oxford     # just one, keeping the rest
FRESH=1 node scripts/build-regional-buses.mjs    # ignore the cache
```

Adding an area is one entry in `AREAS` plus a colour in `AREA_COLOR`. Keep the
box around the built-up area and its park-and-ride rather than around the
county: the point is the buses you would change onto off a train. Avoid
overlapping Greater London if you can — routes tagged `network=London Buses`
are filtered out, since they are already in the TfL catalogue with live
vehicles behind them, but every one still costs a relation in the listing.

OSM splits a route into one relation per direction and often several more per
variant. The builder folds them together on route number and operator, keeps
the four longest, and labels them alternately outbound and inbound.

Coverage is only as good as the mapping, and it is uneven: Oxford's 56 routes
all came through complete, while six Cambridge services exist in OSM only as a
two- or three-stop fragment somebody began and never finished. Anything whose
longest direction has fewer than `MIN_STOPS` stops is dropped and listed at the
end of that area's build, because a line claiming a bus runs two stops and then
gives up is worse than not offering the route.

## Live vehicles

A vehicle between two stops is drawn as an arrowhead pointing the way it is
going. It used to be a rotated pill, and a pill rotated 15° is the same picture
as the same pill rotated 195° — which end of the line a train is heading for is
the one thing a moving dot has to answer. Position itself is unchanged:
`computeTrainLatLon()` still integrates along the track between the two stops.

An estimated position — anything from Darwin, or from a TfL arrival prediction
rather than the live vehicle feed — is faded rather than dashed. A dashed
outline on a pill was a hint; on an arrowhead it is six dashes around a spike,
which at map density reads as a rendering fault.

### Where a vehicle is going, and when

Both the strip across the top of the vehicle panel and the calling list below
it come from one call to `vehicleCalls()`, so they cannot disagree about which
branch the vehicle is on. They used to guess separately, which is how the strip
ended up running the opposite way to the list beneath it.

`routeForVehicle()` picks the branch by scoring every published route on how
many of the vehicle's own predicted stops it contains, in order. Matching on
one station — what `findBestRoute()` does, and all it can do — cannot tell a
Northern line train via Bank from one via Charing Cross.

Times come from whichever feed has them:

| Source | Gives us | Which vehicles |
| --- | --- | --- |
| Darwin | scheduled, estimated and actual times for the whole booked route | National Rail |
| `Line/{id}/Arrivals` | live predictions, grouped by `vehicleId` | tube, DLR, Overground, Elizabeth, tram, river, London buses |
| modelled | the vehicle's own pace | anything the other two do not cover |

TfL's flat per-line arrivals response reconstructs one vehicle's remaining
calls once it is grouped by `vehicleId` — and that is the same id the live
vehicle feed uses, so an SSE train can borrow predictions it does not carry
itself. One request covers every train on the line, cached for 30 s; the bus
and river pollers already hold one, so they file theirs rather than have the
panel fetch it again.

Predictions only run about half an hour ahead, so a train at the top of the
Northern line has times for its next dozen stops and nothing for the rest of
Zone 1. Those gaps are filled by interpolating **between the predictions either
side of them**, not by walking outwards from where the train is now — the
latter puts a modelled 08:25 between a predicted 08:03 and a predicted 08:06.
A final pass holds the list monotonic, because the feed does briefly report a
train's next stop as earlier than the one it is standing in.

### Route dropdowns on the line page

TfL publish a line's *service patterns*, not its branches, so the Northern line
arrives as 22 routes where a reader would recognise about ten. `linePageRoutes()`
folds identical patterns together — Euston → Morden is listed three times — and
drops any pattern that is a contiguous run inside a longer one going the same
way, which is a short working rather than a different railway. Twenty-two
becomes twelve, each a `<details>` labelled by its termini, with *via* the first
stop that tells two same-terminus patterns apart. The longest pattern each way
starts open; the rest render their stops only once opened.

## Crowding

Two feeds, covering different halves of the question.

**Stations** come from TfL's Crowding API: `crowding/{Naptan}/Live` for now,
`crowding/{Naptan}/{Day}` for how busy that station usually is at each quarter
hour of that weekday. Underground stations only — the API answers
`dataAvailable:false` for National Rail, DLR and Overground naptans rather than
404ing, and the panel shows nothing rather than a zero.

Both numbers are a percentage of *that station's own* baseline, so they compare
a station with itself and with nothing else: 22% of baseline is High Barnet at
the height of the morning peak and Oxford Circus on a slow afternoon. No
absolute reading of "busy" survives that, so the scale is the station's own day
and the words say so — a station at the top of it is at *its* busiest, which at
Chesham on a Monday morning is a dozen people on a platform. The literal
crowd-size question is one the open data cannot answer, and the panel does not
pretend otherwise. The live figure is also read against the typical figure for
the same quarter hour, which is the one comparison the two feeds support
cleanly: *36% busier than usual*.

**Trains** come from Darwin's `formation`: a loading percentage per coach and
an average for the train. About 45% of services carry it — Southeastern,
Thameslink, c2c, Greater Anglia and Elizabeth line mostly do — and where the
per-coach figures are there they are drawn as a row of bars, which is the
difference between "this train is full" and "walk to coach B". That is a real
proportion of a real train, so it gets plain words (*Standing room*, *Very
full*) where the station scale cannot.

Nothing publishes live loading for an Underground train; TfL never have. Those
fall back to the live crowding of the stop the train is pulling into, labelled
as that and not as the train.

## Journey planner

Routes, times and fares all come from TfL's own journey planner
(`api.tfl.gov.uk/Journey/JourneyResults`) rather than from the network graph in
this folder. Nothing in the planner estimates a price: TfL return the exact pay
as you go cost of each option, peak and off-peak, in pence, for the departure
they were asked about.

Each search fires three requests — `LeastTime`, `LeastInterchange` and
`LeastWalking` — and merges them, deduplicated on the sequence of lines ridden.
One preference on its own mostly returns the same route at three departure
times; merging the three is what makes the result a choice. The **Prefer** chips
then sort what came back, including by price, which is a local sort and costs no
extra request.

The mode chips go straight into the request's `mode` parameter, with `walking`
always appended. They are remembered in `localStorage['tt-jp-options']`.

### Fares

| What | Where it comes from |
| --- | --- |
| Single fares, peak and off-peak | TfL journey planner, live, per option |
| Which rate applies to this departure | TfL's `chargeLevel` on the fare |
| Zones travelled through | TfL's `lowZone` / `highZone` on the fare |
| Hopper fare | TfL's `isHopperFare` on the fare |
| Daily caps | `CAP_PEAK_P` / `CAP_OFFPEAK_P` in `index.html` |

The caps are the one thing the API does not return, so they are a table in the
page, taken from TfL's published *Adult rate prices 2026* card
(`content.tfl.gov.uk/adult-fares.pdf`) and indexed by the highest zone a journey
touches — the only thing TfL's own table varies by. Peak and off-peak caps are
identical up to Zone 6 and only diverge from Zone 7 out. When fares change,
those two arrays and `FARE_CARD` are what needs editing; everything else
re-prices itself.

Peak is Monday to Friday, 06:30–09:30 and 16:00–19:00. The page only models
those windows to work out how long a peak fare has left to run — that is what
the "wait for off-peak" nudge counts down, and its *Re-plan* button re-runs the
search for the moment the cheaper fare starts. The exceptions to the windows
(public holidays, and journeys into Zone 1 during the evening peak) are TfL's
to apply, and they do, in the price they return.

### Rate limits

TfL throttle anonymous callers, and a search costs three requests, so a burst of
re-planning can earn an HTTP 429. A free key from
[api-portal.tfl.gov.uk](https://api-portal.tfl.gov.uk) lifts that without the
page shipping anyone's credentials:

```js
localStorage['tt-tfl-app-key'] = 'your key';
```

When TfL cannot be reached at all, the planner falls back to the local graph in
this folder: one route, times modelled from distance at typical line speeds, no
fares, and a card that says as much. The fallback honours the same mode chips as
the live search.

## Bike share

The Bike row in the layer tray has five operators. Only two of them can be
drawn from open data today:

| Operator | Feed |
| --- | --- |
| Santander Cycles | TfL BikePoint (docks, live availability) |
| Beryl | public GBFS — the London, Hackney Cargo Bike and Barnet schemes |
| Lime | partner GBFS only (`gbfs_transit`), needs credentials |
| Forest | no public feed — shared with TfL and the boroughs |
| VOI Bike | UK GBFS is issued per partner, needs a key |

The three without a feed still get a pill, dimmed, and the tray says why. To
point one at a feed — a partner URL, or a proxy of your own — set an override
in the browser and reload:

```js
localStorage['tt-bike-feeds'] = JSON.stringify({
  'lime-bikes': 'https://example.com/lime/gbfs.json',
  'forest-bikes': ['https://example.com/forest/gbfs.json'],
});
```

Anything GBFS 2.x or 3.x works: the reader follows `gbfs.json`, then reads
`station_information` + `station_status` for bays and `free_bike_status` (or
`vehicle_status`) for bikes left on the street, filtering out scooters and
mopeds via `vehicle_types` where the operator publishes it. Permanent feeds
belong in `BIKE_OPERATORS` in `index.html`.

## Marker shapes

Bike operators share one colour scale — green for plenty, amber for nearly
empty, red for none — so colour cannot also carry *whose* bike it is. Each
operator gets a shape instead, and the same shape appears on its tray pill, in
the nearby list and in the panel header:

| Operator | Shape | Operator | Shape |
| --- | --- | --- | --- |
| Santander Cycles | circle | VOI | diamond |
| Lime | square | Beryl | pentagon |
| Forest | triangle | | |

Taxi layers use the same vocabulary: ranks are hexagons, minicab offices are
inverted triangles, roaming ride-hail cars are octagons.

`ShapeMarker` subclasses Leaflet's `CircleMarker` and overrides `_updatePath`
only, so the shapes keep Leaflet's pane, culling and event handling and stay a
constant pixel size at every zoom. Polygons are scaled to match the *area* of
the circle they replace (`ngonScale`), not inscribed in it — inscribing makes a
triangle read as roughly half the weight of a square sitting next to it.

## Taxis

The Taxi row has three layers. Two are real TfL open data, fetched once and
cached in `localStorage` for 30 days, since ranks move perhaps twice a year:

| Layer | Source | Count |
| --- | --- | --- |
| Ranks | `Place/Type/TaxiRank` | 580 (545 hailable; the rest are rest and refreshment ranks) |
| Minicabs | `Place/Type/Cabwise` | 625 licensed private hire offices |
| Uber | — | no data source |

Both responses are trimmed on arrival before caching — Cabwise alone is ~5 MB
raw and almost all of it is fields the panel never shows.

**Uber is a wired-up slot, not a live layer.** No ride-hailing operator
publishes vehicle positions openly: Uber's API is OAuth-only and answers "how
long until a car reaches this point", not "where are the cars", and there is no
feed behind `gbfs.uber.com`. Lime, VOI, Dott and Forest were checked too and all
return 401 or 404 for London. So the layer draws nothing and says why on its own
pill, rather than inventing cars on a public map.

The intended source is the visitor linking their own Uber account. Everything
downstream of that — markers, panel, the nearby list — is already built and
waiting on an adapter:

```js
ttTaxi.register('uber', {
  label: 'Uber',
  // → [{ id, lat, lon, product, plate, etaSeconds, bearing }]
  vehicles: async (bounds) => [...],
  disconnect: () => {},
});
```

That needs an OAuth redirect and a token exchange, which needs a server; this
page is static, so it is not wired up. A second provider (Bolt, FREENOW) costs
one entry in `TAXI_OPERATORS` plus an adapter.

## Nearby

Each station, stop, bike and rank panel opens with a collapsible **Nearby**
list: tube and rail, bus stops, bikes, river piers and taxi ranks within 650 m,
in both directions — buses from a tube station, tube stations from a bus stop.

It deliberately does not rely on what the map has already loaded, because bus
stops only exist in `stationCoords` once you have added that route and the taxi
layer is off by default. Buses, bikes and ranks come from TfL's radius searches
(`StopPoint`, `BikePoint`, `Place`), cached per rounded coordinate; stations and
piers come from memory. A rank that names its station via `StationAtcoCode` — 103
of the 580 do — is shown as *at station* rather than given a walking distance.

## Airports

Six airports — Heathrow, Gatwick, Luton, Stansted, London City and Southend —
each get a departure and arrival board in the station panel, and a pin on the
map. `AIRPORTS` in `index.html` holds the whole list; adding a seventh is one
entry plus whatever its rail station is called in the network data.

The two pills in the **Air** tray row are pseudo-lines with no route geometry:
`airports` toggles the terminal pins, `flights` toggles the live aircraft. The
airports are registered in `stationCoords` as stations, which is what gets them
search, favourites, `#LHR` deep links and journey planning for free —
`showStationPanel()` intercepts them and opens a flight board instead of a train
board.

| Source | Gives us | CORS? |
| --- | --- | --- |
| Avionio widget | scheduled + estimated boards, status, codeshares | no |
| Avionio flight page | terminal, 14-day punctuality history | no |
| adsb.lol | live aircraft within 90 nm of London | no |
| adsbdb | callsign → airline + route, registration → airframe + photo | yes |

Three of the four send no `Access-Control-Allow-Origin`, so they are fetched
through a chain of public CORS relays (`AIR_PROXIES`), the same
try-then-remember pattern as `darwinBases()`. In local development
`scripts/local_server.py` proxies them itself at `/proxy?url=…` against a host
allowlist, which is faster and does not burn someone else's free tier.

Two things worth knowing before changing the flight detail panel:

**Avionio's flight page is not today.** `/en/flight/ba-117` renders one past
instance — usually the oldest row of its own history table, a fortnight back —
while the history table below it is current. So the headline card's times,
status and gate are not today's. `flightLegs()` builds each leg from the board
row first, then that day's history row, and only trusts the card when
`cardDate` matches the day being shown. Gate numbers are dropped outright;
terminal is carried over and labelled *usual terminal*, because which terminal a
flight uses barely changes.

**Callsigns are not flight numbers.** The board says `BA117`; ADS-B broadcasts
`BAW117`. `AIRLINE_ICAO` maps the carriers that serve these airports, and
`AIRLINE_ICAO_ALT` covers the ones that fly under more than one prefix (BA
short-haul is `SHT`, some BA-numbered flights are CityFlyer `CFE`, easyJet has
three AOCs). Anything missing is learned from adsbdb on first lookup. easyJet is
the known gap: `U2 8629` flies as `EZY67PH`, so its number cannot be matched at
all, and those rows simply get no **LIVE** badge.
